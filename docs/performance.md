# 성능 작업 기준과 검증

기준일: 2026-10-06 KST. 최신 소스는 사용자 확인한 D 프로젝트 루트다. **19:45:10 사용자 정정: 성능 대상은 WASD로 이동하며 바닥 파일을 집어 상자에 넣는 실제 Three.js 게임만이다.** 랜딩 디자인·기획은 Claude 작업으로 분리한다. 이전 랜딩 최적화 기록은 Codex가 범위를 잘못 확대한 이력이며 이후 게임 최적화에 포함하지 않는다. 게임 1차 변경은 적용했지만 학교 PC 성능 개선은 아직 측정하지 않았다. 추가 측정/최적화는 새 채팅에서 이어간다.

## 입력 반응

기존 시점은 입력 잔여의 38%를 매 프레임 반영했다. 낮은 FPS에서는 같은 마우스 이동을 따라가는 시간도 늘어났다. [LookInput](../js/three/look-input.js)은 포인터락 입력을 **다음 렌더 프레임에 전부** 반영하고, 커서 드래그에는 `1 - (1 - smoothing)^(dt × 60)`을 사용한다. 감도·방향·pitch 범위·걷기 속도는 유지한다.

[SceneKit](../js/three/scene-kit.js)이 실제 카메라에 연결하고, [Board3D](../js/three/board-3d.js)가 카메라/잠금/blur/suspend 전환에서 잔여와 활성 시점 드래그를 정리한다. blur 후 버튼을 놓았어도 이전 우클릭 드래그가 이어지는 경로는 별도 읽기 검토에서 발견해 함께 수정했다.

이는 입력 보간 지연 제거다. GPU가 다음 프레임을 늦게 그리는 문제까지 없앤다는 뜻은 아니다. 30/60/120fps 동일 시간 응답과 포인터락 잔여 제거는 단위검사로 확인한다. 일반 브라우저의 실제 pointer lock, 학교 PC에서의 마우스 응답은 별도 현장 검증 대상이다.

## Three.js 화면 품질

[품질 정책](../js/three/render-quality.js)은 CSS 화면 크기를 유지하면서 drawing buffer의 픽셀 수를 제한한다. [설정 패널](../app.html)의 ‘화면 품질’ 또는 `app.html?entry=sample&storage=memory&quality=low`로 비교한다.

| 설정 / 내부 단계 | 최대 DPR | 최대 버퍼 픽셀 | 그림자 한 변 | 질감 필터 배율 / 긴 변 상한 | 후처리 |
| --- | ---: | ---: | ---: | --- | --- |
| 선명하게 / high | 2 | 4,000,000 | 2048 | .75 / 1600 | 기존 질감·외곽선 설정 사용 |
| 자동 초기 / balanced | 1.5 | 2,000,000 | 1024 | .6 / 1200 | 기존 질감·외곽선 설정 사용 |
| 가볍게 / low | 1 | 1,000,000 | 512 | 실행하지 않음 | 질감 필터와 외곽선 패스 생략 |

자동 모드는 실제 프레임 간격을 2초 단위로 모은다. 평균이 27ms를 넘는 창을 관찰하면 low로 내려 이번 세션 동안 유지한다. 단발성 지연, 숨겨진 탭, 250ms를 넘는 중단은 측정에서 제외한다. 사용자가 선명하게/가볍게를 고르면 자동 변경하지 않는다. 다시 자동을 고르면 새 측정을 시작한다.

가볍게는 종이 재질·색·가구·파일 조작을 유지하지만 붓결과 외곽선은 줄어든다. 비활성 스타일 조절칸과 현재 품질 설명을 함께 표시해 선택값과 실제 효과가 혼동되지 않도록 했다. 품질 전환 시 shadow map 자원을 해제하고 새로운 크기로 생성한다.

파일 hover 라벨의 `strong`/`small` 노드를 재사용하고 내용이 바뀔 때만 text를 바꾼다. 위치는 계속 시점을 따라간다. 숨겨진 문서에서는 Three 렌더 작업을 건너뛴다.

## 랜딩 자산과 준비 시점

승인된 일러스트 15개는 **lossless WebP**로 인코딩했다. 원본 PNG는 제작·디자인 작업용으로 보관한다. 원본 해시, 출력 재읽기, 크기·전체 RGBA·alpha 동일 여부는 [에셋 보고서](../tools/landing-assets-report.json)에 기록하고 [변환 도구](../tools/optimize-landing-assets.py)로 다시 확인할 수 있다. 새로운 그림을 생성하거나 파츠 좌표를 바꾸지 않았다.

| 파일 바이트 합계 | 이전 | 현재 | 변화 |
| --- | ---: | ---: | --- |
| 런타임 PNG 15개 → WebP 15개 | 22,800,210 | 16,098,554 | 29.39% 감소 |
| 첫 방 이미지 5개 | 3,592,786 | 2,485,602 | 30.82% 감소 |
| 첫 방을 보이기 전 이미지·서체·manifest 의존성 | 14,493,713 | 2,558,990 | 약 82.34% 감소 |

마지막 행은 기존 room 5개 + 탑뷰 box 6개 + 서체 + manifest에서, room 5개 + 서체 + manifest로 바뀐 준비 의존성의 비교다. HTML/CSS/JS 등은 포함하지 않는다. **실제 네트워크 전송량/로딩 시간/FPS 측정값이 아니다.** 전체 저장소는 원본 PNG와 WebP를 함께 보관하므로 저장소 용량이 이 비율로 줄었다고 해석하지 않는다. WebP는 같은 크기로 디코딩하므로 이미지의 RGBA 메모리 자체를 줄이는 변경도 아니다.

**2026-10-06 Claude 정정:** 위 표는 코드가 기다리는 의존성 기준이었고, 실제로는 `index.html`이 쓰지 않는 PNG 3개(4,228,441 B)를 따로 preload해 첫 방 전 로컬 요청 합계가 6,927,659 B였다. preload를 실행 WebP 5개 + 서체로 바꾼 뒤 2,699,218 B. 상세는 [랜딩 재설계 방향](landing-redesign.md) 6절. 로컬 서버 파일 크기 합이며 네트워크 시간 측정이 아니다.

처음에는 방 이미지와 서체만 준비한다. 상자 낙하 때 탑뷰를 준비하고 상자 클릭 전환은 준비 완료를 기다린다. 선택 때 바탕화면을, 모니터 진입 때 복귀 장면을 준비한다. `.ready`와 멱등 `.prepare()`는 준비 결과와 오류를 유지한다. 프리뷰의 기본 eager 준비는 유지한다.

정지한 첫 방/착지 상자와 테이프는 Canvas 프레임을 계속 그리지 않는다. 포인터/hover/드래그/resize/초기화/장면 전환에서 다시 깨우고 모션이 끝나면 멈춘다. 이미지의 준비 여부와 활성 장면은 따로 관리한다. Canvas backing buffer 한도와 CSS 좌표는 분리해 포인터·히트 영역을 유지한다.

## 검증 기록

최종 실행 결과와 원본 반영 시각은 [작업 타임라인](agent-timeline.md)에 기록한다. 테스트는 임시 폴더와 샘플을 사용한다. 실제 바탕화면 파일을 이동하는 방식으로 검사하지 않는다.

이번 검증에는 입력 누적/시간 보정, 품질 예산/자동 단계, 장면별 지연 준비, 유휴 RAF와 이벤트, 기존 파일 처리/랜딩 상태 회귀검사 및 브라우저 기본 여정을 포함한다. 버퍼 한도 검사는 실제 buffer 크기와 DOM 상태를 읽어 확인한다.

학교 PC의 FPS·GPU 메모리·input-to-photon 지연은 아직 측정하지 않았다. Codex 인앱 브라우저에서 pointer lock이 거부되어 대체 UI가 표시된 결과를 일반 브라우저의 포인터락 성공으로 보고하지 않는다. 좁은 화면의 버퍼 크기 검사는 모바일 테이프 구도·터치 사용성 검증을 대신하지 않는다. 테이프 잡힘/당김 개선은 디자인 후속 작업이다.

## 학교 PC에서 비교할 순서

1. 같은 화면 크기, 같은 샘플 45개에서 자동/선명하게/가볍게를 각각 비교한다.
2. Chrome/Edge에서 pointer lock 상태로 10–30초 둘러보고 마우스를 멈춘 뒤 시점이 계속 따라오는지 확인한다.
3. DevTools Performance에서 frame time 평균과 p95, CPU/GPU 작업과 긴 프레임을 기록한다. 질감 off/외곽선 0을 각각 비교할 때는 선명하게 모드를 사용한다.
4. 원인·품질 타협을 확인한 후 예산/자동 전환 기준을 조정한다. 코드 1만 줄·파일 2–5MB 자체를 렌더 성능의 고정 한계로 정하지 않는다.

새 에이전트는 숫자를 바꾸기 전에 실제 코드와 최신 로그를 확인하고 측정 환경·샘플·시각을 함께 남긴다.


## 실제 게임 후속 측정 · 2026-10-06

[후속 측정 기록](game-performance-20261006.md)에 원본 JSON·측정 조건·검증·학교 PC 절차를 남겼다. D 최신본에서 전체 테스트 274/274와 샘플 집기/넣기를 확인했다.

집기 때 전체 방 대신 카메라/판정 대상의 행렬만 갱신한다. 실제 정적 장면의 200개 광선 결과는 일치했고, 6회 교차 비교 평균 CPU는 0.03475→0.01025ms/판정이었다. 시각 품질은 바꾸지 않았다. 전체 FPS가 그 비율만큼 증가한 결과는 아니다.

`profile=1`은 10초 CPU/GPU/프레임/외부 pick 측정과 JSON 저장을 제공한다. high/low/high-off 모두 로컬 RAF 평균 약 8.34ms였으므로 추가 FPS 향상을 관찰하지 않았다. 일반 포인터락/물리 입력/학교 PC는 계속 미검증이다. 랜딩은 이번 후속 작업에서 변경하지 않았다.

## 기기별 자동 화질 · 2026-10-11 (Claude)

사용자 요청: "기기별 성능에 따라 최적화, 3D니까 해상도를 낮춘다거나". 정리방과 랜딩이 같은 `js/three/render-quality.js`를 쓴다.

- 처음 단계(`deviceTier`): WebGL `UNMASKED_RENDERER` 이름 + `hardwareConcurrency`·`deviceMemory`·거친 포인터. SwiftShader·llvmpipe 등 소프트웨어 GL → low, Intel·Mali·Adreno 등 내장 → balanced, NVIDIA·Radeon RX·Apple M → high. 4코어·4 GB 이하는 high를 balanced로, 2코어·2 GB 이하는 low.
- 실제 프레임: 1.5초 창 평균이 23.5 ms(≈43fps)를 넘으면 해상도 배율 −12.5%(high 최저 0.75, balanced 0.625, low 0.5), 바닥이면 한 단계 아래 프로필. 18.5 ms 아래를 몇 창 연속 지키면 배율 +12.5%. 느려질 때마다 다시 올리는 데 필요한 창이 두 배(3 → 6 → 12, 최대 48). 프로필 단계는 내려가기만 한다.
- 프로필: high(DPR 2, 4 MP, 그림자 2048), balanced(DPR 1.5, 2 MP, 1024), low(DPR 1, 1 MP, 512, 그림자 3프레임에 한 번, 햇살 줄기·외곽선·디더링 끔, 랜딩 스탠드 점광원 그림자 끔).
- 그림자: 정리방은 `shadowMap.autoUpdate = false` + 프로필의 `shadowEvery` 프레임마다 갱신(high·balanced는 매 프레임이라 예전과 같음). 랜딩의 방은 움직이지 않아 빛·방 상태가 바뀔 때만 다시 그린다(밤 장면의 점광원은 그림자 6면을 그리므로 차이가 크다).
- 고정: 정리방 `?quality=high|low`, 랜딩 `?render=high|low`(index.html의 `?quality=`는 앱으로 넘어가는 예전 주소라 이름을 달리함). 설정 패널의 ‘화면 품질’ 상태에 해상도 배율이 같이 보인다.
- 다운로드: `room.glb` 4.4 → 3.1 MB(금속·거칠기 PNG → JPEG ≤1024 px, 툰 그림은 그 텍스처를 안 씀), 노트북 안 바닥 1.4 MB → 74 KB, 가져오기 화면 그림 4장 2.4 MB → 0.33 MB(WebP 손실 압축).
- 확인: `tests/render-quality.test.js`(단계 짐작, 배율 → 단계 순서, 되돌아오기, 수동 고정). 헤드리스(소프트웨어 GL)에서 자동이 low로 시작함을 확인. **실제 GPU에서의 프레임과 단계 전환은 미확인** — 학교 PC·노트북에서 `?profile=1`과 설정 패널 상태로 확인할 것.
