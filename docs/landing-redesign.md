# 랜딩 재설계 방향 — 제안

## 1. 측정한 현재 흐름

D 최신본을 클라우드에 복제해 headless Chromium으로 랜딩을 처음부터 끝까지 실제 입력으로 진행했다. 1920×1080, 1366×768, 390×844. 실측 근거는 아래 표의 수치와 [흐름 캡처](design/landing-audit-20261006.jpg). 학교 PC·실제 마우스·터치 기기 결과가 아니다.

- **합계:** 입력 9회(스크롤 1, 클릭 3, 테이프 2, 수거 3). 동사 4종(스크롤·클릭·당기기·훑어 담기). 사용자 입력과 무관한 고정 연출 약 7.4초 + 아이콘 낙하.
- **390×844:** 탑뷰에서 테이프 손잡이가 x=−242px, 화면 밖이다. 포인터로는 진행할 수 없다(키보드 Enter/Space만 가능).

## 2. 진단

1. **힌트 하나가 빠진 게 아니라 ‘동사 맞히기’가 네 번 반복된다.** 정지 지점마다 요구하는 동작이 다르고(클릭 → 당기기 → 클릭 → 클릭), 그때마다 화면의 물체는 가만히 있다. 교수 피드백 “다음에 뭘 해야 할지 모르겠다”는 이 구조의 결과다. 힌트를 더하는 것보다 정지 지점과 동사 수를 줄이는 쪽이 효과가 크다.
2. **테이프는 힌트와 손잡이가 어긋난다.** 호버 힌트는 테이프 전체에서 켜지는데 잡히는 곳은 왼쪽 끝뿐이다. 가장 자연스럽게 잡을 곳(‘Cozium’ 글자가 있는 가운데)은 반응하지 않는다. 완료 거리는 화면 폭의 60%라 한 번에 끝내기 어렵다.
3. **랜딩의 수거 조작은 실제 게임 조작과 다르다.** 랜딩은 2D 드래그 앤 드롭 + 자석, 게임은 1인칭 조준선으로 누른 채 훑기 → 상자 클릭이다. 랜딩을 조작 튜토리얼로 보기는 어렵다. 랜딩의 역할을 “이사 메타포와 정리 전후의 감정 → 시작 버튼”으로 두면 수거 단계를 짧게 해도 잃는 것이 적다.
4. **모바일은 탑뷰에서 막힌다.** 원화를 cover로 채우는 구도라 세로 화면에서 테이프 끝이 잘린다. 정리 앱 자체가 ‘Chromium 데스크톱 전용’이라 랜딩의 모바일 범위를 먼저 정해야 한다.

## 3. 방향 3안

| | A. 정지 지점에 힌트만 | **B. 임의 게이트 제거 + 수거 단축 (추천)** | C. 도입부만 남기기 |
| --- | --- | --- | --- |
| 흐름 | 지금과 같음 | 방 → 착지 상자 클릭 → 테이프 → (자동) 바탕화면이 쏟아짐 → 수거 1~2번 → (자동) 닫힘·복귀 → CTA | 방 → 착지 상자 클릭 → 테이프 → 열리면 정리된 방 + CTA |
| 입력 수 | 9 → 8 (테이프 1번) | 9 → 5 | 9 → 3 |
| 정지 지점 | 4곳 그대로, 넛지 추가 | 2곳(착지 상자, 테이프) | 2곳 |
| 유지 | 승인된 장면·클릭 분기 전부 | 상자를 여는 결심(클릭), 테이프, 훑어 담기 | 상자를 여는 결심, 테이프 |
| 잃는 것 | 길이·피로는 그대로 | 바탕화면 클릭·닫힌 상자 클릭의 수동 리듬 | 바탕화면·수거·복귀 장면(코드·에셋은 보관). “담았더니 방이 정리됐다”는 인과가 약해짐 |
| 작업량 | 작음 | 중간 | 중간~큼 (새 전환 필요) |

**B를 추천하는 이유.** 이 프로젝트의 성패는 손맛이다([CLAUDE.md](../CLAUDE.md) §2). 랜딩에서 손맛을 보여 주는 순간은 테이프와 훑어 담기 두 개다. B는 그 둘을 남기고, 의미 없이 멈추는 클릭 두 개(바탕화면, 닫힌 상자)만 자동으로 바꾼다. 착지 상자 클릭은 “상자를 열기로 한다”는 결심이라 남긴다. C는 가장 짧지만 정리 전후의 인과가 빠져 마지막 정리된 방이 ‘그냥 다른 그림’이 된다.

B의 세부 `[임시]`:

- 바탕화면: 모니터 전환이 끝나고 0.6초 뒤 아이콘이 자동으로 쏟아진다(지금의 낙하 연출을 그대로 자동 재생).
- 수거: 2번 안에 끝나게 한다. 방법은 둘 — 아이콘 수 80 → 약 40, 또는 80개 유지 + 한 번에 담기는 양 28 → 45. 어지러운 바탕화면의 인상을 지키려면 후자.
- 마지막 묶음이 들어가면 덮개가 닫히고 0.5초 뒤 자동 복귀.

## 4. 어느 안이든 공통으로 할 것

### 4-1. 대기 넛지 — 비언어 힌트

사용자 확인 규칙을 그대로 지킨다: 지시 문구 없음, 손 그림 없음, 물체 반응과 커서로 전달.

- **조건:** 정지 지점에 들어와 필요한 동작 없이 2.5초가 지나면, 다음에 만질 물체가 스스로 움찔한다. 이후 +4초, +6초, 최대 3번. 포인터가 그 물체 위에 있으면 넛지 대신 기존 호버 반응을 쓴다.
- **착지 상자:** 바닥에서 4px 들썩, 그림자가 줄었다 돌아옴(약 450ms).
- **테이프:** 지금의 호버 리프트를 자동으로 한 번 재생(들렸다 내려앉음, 약 700ms).
- **A안을 고를 때만:** 바탕화면 아이콘 2~3개가 기울며 흔들림, 닫힌 상자 덮개가 톡 튐.
- **reduced motion:** 움직임 대신 대상의 그림자·윤곽을 정적으로 진하게.

### 4-2. 테이프 `[임시]`

- 잡히는 곳 = 힌트가 켜지는 곳: 테이프 전체(1920 화면 약 1099×166px). 커서도 테이프 전체에서 `grab`. 어디를 잡든 끝에서부터 벗겨지고, 잡은 점과 끝 사이의 거리는 유지한다.
- 완료: 놓을 때 50% 이상이면 남은 부분이 자동으로 벗겨짐(약 400ms). 50% 미만이면 지금처럼 그 자리에 머문다.
- 당김 거리: 테이프 폭 × 1.3(최대 1360px) → 테이프 폭 × 0.9(최대 1000px). 1920 화면에서 50%는 약 495px(폭의 26%), 1366 화면은 약 352px.
- 키보드 Enter/Space 대체 입력은 유지.

### 4-3. 좁은 화면 — 결정 필요

- **(a) 랜딩을 데스크톱 체험으로 명시:** 세로·좁은 화면은 첫 방과 정리된 방 + CTA만 보여 주고, 상자 체험은 넓은 화면에서만. 정리 앱이 데스크톱 전용이라 일관되고 작업이 작다.
- **(b) 세로 화면용 탑뷰 구도:** 테이프가 화면 안에 들어오도록 탑뷰만 contain 기준으로 다시 맞추고, 바탕화면·수거도 세로 배치를 따로 만든다. 작업이 크다.

## 6. 이번에 고친 것 (방향과 무관한 버그)

`index.html`이 실행에 쓰지 않는 PNG 3개(방 배경, 방 상자, 탑뷰 바닥 — 4.23MB)를 preload하고 있었다. 런타임은 WebP를 쓰므로 같은 그림을 두 번 받았고, 탑뷰 바닥은 ‘장면별 지연 준비’ 설계와도 어긋났다. Chromium도 “preload했지만 쓰지 않음” 경고를 6건 냈다. 첫 방을 그리기 전 hero.js가 기다리는 WebP 5개와 Fraunces 서체만 preload하도록 바꾸고, [회귀 테스트](../tests/landing/preload.test.mjs)로 잠갔다.

| 로컬 Chromium 요청 기준 | 이전 | 이후 |
| --- | ---: | ---: |
| 첫 방이 준비될 때까지 받은 파일 | 6,927,659 B (27건) | 2,699,218 B (24건) |
| 랜딩 끝까지 받은 파일 | 20,593,317 B | 16,364,876 B |
| preload 미사용 경고 | 6 | 0 |

바이트는 로컬 서버 응답 파일 크기의 합이다. 실제 네트워크 시간·학교 PC 로딩 시간 측정이 아니다.
