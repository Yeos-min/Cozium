## 제품의 감각

**사용자 확인:** 파일과 폴더는 이삿짐이고, 정리는 그 물건들이 제자리를 찾는 행동이다. 실제 파일을 드래그해 가져오는 경험과 이사라는 은유를 이어 준다. 랜딩은 같은 방의 정리 전후를 보여 주고, 실제 앱은 파일을 집어 폴더로 옮기는 조작을 맡는다.

따뜻한 햇빛, 밝은 나무 바닥, 종이와 크래프트 상자, 깊은 녹색 식물이 시각적 중심이다. 방의 원근과 가까운 전경이 화면의 깊이를 만든다. 식물과 비네팅은 가장자리에서 중심을 잡아 주는 요소다. 별도의 작은 액자 안에 장면을 가두는 방식은 사용자가 말한 ‘프레임’의 뜻이 아니다.

사용자가 선택한 [Nomadic Tribe 레퍼런스](https://www.makemepulse.com/case-study/nomadic-tribe)는 장면 중심의 디자인과 이야기 전환을 위한 참고다. 그 사이트의 에셋·캐릭터·구성을 복제하는 지시가 아니다. 처음 제공한 무드보드는 코지한 색과 일러스트의 참고이며, 이후 사용자가 통과시킨 가로형 방과 상자 에셋이 현재 구현의 직접적인 기준이다.

### 구도와 표현

- **가로 웹 화면:** 화면을 채우는 장면으로 설계한다. 정사각형 일러스트를 늘어놓는 구성을 기본으로 삼지 않는다. 원화 기준은 1672 × 941이다.
- **동일한 공간:** 첫 방과 정리된 방의 시점·빛·가구가 연결되어야 한다. 상자는 같은 물건으로 읽히도록 크기, 원근, 바닥 접점과 그림자를 맞춘다.
- **가까운 상자에도 바닥 여백:** 클릭 후 탑뷰에서는 주변 바닥이 조금 보인다. 이후 모니터로 들어가는 전환에서 확대된다. 처음부터 상자로 화면 전체를 채우지 않는다.
- **실제 손 일러스트 없음:** 커서, 물체의 반응과 이동으로 조작을 전달한다. `tuning.js`의 `hand`는 들고 있는 카드의 자리·움직임 이름이며, 실제 사람 손 그림을 넣으라는 뜻이 아니다.
- **차분한 표면:** 종이결과 잉크선은 원화와 기존 SVG의 농도를 참고한다. 새 광택, 과한 입체 효과, 반복 장식, 별개의 캐릭터를 승인 없이 추가하지 않는다.

## 레이아웃과 구성 요소

### 장면

이전 랜딩(`landing-classic.html`)은 sticky `100svh` 장면 위에 Canvas와 HTML을 합성한다. 현재 랜딩의 합성은 위 [현재 랜딩](#현재-랜딩-2026-10-07-교체)의 ‘표현’. 원화는 화면을 채우도록 배율을 정하고 화면 비율에 따라 일부 가장자리를 자른다. 이것은 임의로 화면을 정사각형으로 만드는 동작과 다르다. 근거: `css/landing.css:3`, [hero.js](../js/landing/hero.js)의 `getRoomMatrix`, [tape-renderer.js](../js/landing/tape-renderer.js)의 `getOverheadMatrix`.

상단 로고·‘내 정리방’ 링크, 큰 Cozium 제목과 짧은 문장, 하단 장면 번호가 HTML로 올라간다. 방의 여백 안에 제목이 놓이도록 런타임이 위치를 맞춘다. 중앙 비네팅은 `transparent 46%`부터 `#102e231b`로 어두워지는 타원형 multiply 레이어다 (`css/landing.css:41`).

- **자동 분류 없음 (사용자 결정 2026-10-07):** 실제 앱에도 랜딩에도 '나머지가 알아서 들어가는' 동작을 두지 않는다. 모든 더미는 사용자가 옮긴다.
- 비언어 힌트: 손에 들면 상자 4개가 차례로 튀어 오르고, 손에서 수납장 쪽으로 점이 올라가다 사라진다(특정 상자를 정답처럼 가리키지 않음, [CLAUDE.md](../CLAUDE.md) §11). 상자 위에서는 이름표에 `+N`. 가만히 있으면 가장 큰 더미가 들썩인다. 막힌 스크롤 3번 + 4초, 또는 Enter → 같은 동작의 시연이 남은 더미를 차례로 넣는다. 스크롤 표시(마우스 아이콘)는 스크롤로 넘어갈 수 있는 장면에서만 1.3초 뒤 나온다. **첫 방(10-20 사용자: 힌트가 너무 빈약)**: 마우스를 크림색 26×42로 키우고 아래에 「스크롤해서 시작」(--ui 13px, 주아 아님). 한 번 넘기면 글은 다시 안 뜨고 마우스는 예전 작은 초록(22×36, 아래 30px)으로 — 밝은 작업표시줄 위에서 크림색이 묻혀서(`story.js` cueLearned, `.cue[data-first]`). 마우스 그림은 사용자가 그림으로 바꿀 예정 — `.cue-mouse` 하나만 갈아 끼우면 된다.
- 손맛: 손에 든 더미는 카드마다 스프링(5.2Hz·감쇠 .6, 위 카드일수록 느림)으로 따라오며 움직이는 쪽으로 기운다. 호버 들림 6Hz·.45, 상자 튀어 오름 3.3Hz·.42, 넣을 때 상자 눌림·출렁임.
- 동작 줄이기(reduced motion): 카메라 이동 없이 종이색으로 잠깐 덮었다가 다음 장면. 직접 담기는 건너뛴다. WebGL이 없으면 정지 이미지와 버튼 하나만 보여 준다. 장면마다 숨김 live 문구(`#sceneStatus`)로 장면을 설명한다.

**표현:**

- (2026-10-11부터) 방과 정리된 방은 3D 다락방(위 ‘3D 방’). 노트북 위 바탕화면은 SVG/HTML을 3D 노트북 화면의 투영된 네 꼭짓점에 호모그래피(matrix3d)로 맞추고, 마지막 20%에서 1.72 : 1 화면을 16:9 판으로 편다. 들어가고 나올 때 방 캔버스에 흐림(최대 6px), 바탕화면 가장자리에 최대 5px 페더. (원화 시절: 1672 × 941 원화 레이어와 그림 속 화면 꼭짓점 `Q_MESSY`, `Q_TIDY`.)
- 바닥·물건·상자는 Three.js(물건·바닥·벽은 빛 계산 없는 MeshBasicMaterial + CanvasTexture, 상자만 툰 + 빛). 탑뷰 카메라 거리를 DOM cover와 맞춰 DOM → WebGL 전환이 이어진다. 바닥 장면 카메라는 화면 비율에 맞춰 더미와 상자가 다 들어오도록 거리를 조정한다.
- **노트북 안 장면 새 모델로 (10-13, 사용자: "상자 디자인이랑 바닥 다 변경됐는데")**: 바닥 = 다락방 마루(room.glb `Room_BaseColor`의 바닥 UV 부분을 잘라 `assets/landing/room-3d/attic-floor.webp`, 1 단위 ≈ 0.47 m로 반복, 판자가 안쪽으로). 상자 = 사용자 `models/box.glb` ×2.6, 툰, 사진·음악·영상은 연두빛, 문서·압축파일은 크래프트 그대로, 손잡이 구멍 아래 이름표(아이콘·이름·개수·`+N`). **수납장은 뺐다** — 게임처럼 상자가 뒷벽 앞 바닥에 한 줄. 상자가 깊어서 담긴 물건은 상자 높이 절반부터 쌓아 테두리 위로 보이게. 예전 원화 바닥 `inside-floor.webp`는 안 씀. 벽(10-13, 사용자 "벽 색이 이게 맞나")도 다락방 것으로: 회벽 `attic-plaster.webp`(room.glb 벽 부분, #f5f0e9) + 진한 나무(Wood beam, #3a2c22) 굽도리·무릎벽 보(1.19 m). 상자 사이 세로 기둥은 넣었다가 뺌(사용자 10-13). 원화 시절 크림색 + 황토 걸레받이는 뺌.
- 전환 중 바닥 번쩍임(10-13 사용자 제보) 원인: 큰 사각형 넷(바닥·바닥 밑 200 m 판·바탕화면 벽지·벽)이 모서리 넷뿐이라 정점 흔들림이 모서리를 따로 옮겨, 기울어지는 동안 바닥 밑 판이 삼각형으로 바닥을 뚫고 나옴. 이 판들은 `userData.noSnap`으로 흔들림에서 뺀다(`js/three/vertex-snap.js`가 건너뜀).
- 상자는 10-13부터 사용자 box.glb(위). 수납장 모델 사양([prototypes/cabinet-model-spec.md](prototypes/cabinet-model-spec.md))은 수납장을 빼면서 쓰지 않음.
- 바닥 원화(`box/box-opening-v1/floor.webp`)는 판자가 16.25° 기울어 있어 돌려서 1.46배 확대해 쓴다(조금 흐림). 판자가 수평인 탑뷰 원화로 바꾸면 해결된다.

**검증 필요:** 실제 트랙패드·마우스 휠에서 한 번에 한 장면만 넘어가는지, 클릭과 끌기 구분(8px), 스프링 손맛, 학교 PC 프레임, 키보드만으로의 여정, 스크린리더 전달. 세로·좁은 화면은 원화를 cover로 잘라 노트북이 화면 밖에 놓인다 — 모바일 버전은 사용자 계획상 나중이다.

## 시각적 힌트와 접근성

현재 랜딩의 힌트는 위 [현재 랜딩](#현재-랜딩-2026-10-07-교체)에 있다. 이 절의 테이프·모니터 관련 구현 설명은 이전 랜딩 기준이다.

**사용자 확인(이전 랜딩 기준, 10-20 현재 랜딩 첫 방은 예외 — 사용자가 「스크롤해서 시작」 글을 요청):** 랜딩에 ‘잡고 당겨’, ‘스크롤 해’라는 직접적인 지시 문구를 디자인 장식으로 넣지 않는다. 테이프 영역에 호버하면 왼쪽 위 끝이 살짝 들리는 것이 조작 힌트다. 실제 손 그림 대신 pointer/grab/grabbing 커서와 물체 반응을 활용한다.

**현재 구현:** 테이프 끝과 상자는 HTML 버튼이고, 모니터 Canvas에는 버튼 역할·키보드 입력과 상황별 이름이 있다. 숨김 live status로 진행을 알리고 포커스 표시를 둔다. CSS와 Canvas 전환은 reduced motion 설정을 일부 반영한다. `aria-label`과 스크린리더 문구는 눈에 보이는 지시 장식을 추가하는 것과 다르므로 유지한다. 근거: [index.html](../index.html), [tape-input.js](../js/landing/tape-input.js)의 `keyDown`, [desktop-interaction.js](../js/landing/desktop-interaction.js)의 `keydown` 처리.

**재설계 대기:** 교수 피드백에서 다음에 무엇을 해야 하는지 여전히 불명확하다는 문제가 나왔다. 이미 있는 호버·커서·휠 모양이 충분하다고 단정하지 않는다. 힌트의 위치·반복·세기, 테이프의 잡히는 범위와 완료 조건, 전체 진행 길이는 다음 디자인 검사 대상이다.

현재 테이프 완료는 드래그를 놓을 때 진행도 .85 이상이며, 저항 거리는 테이프 너비의 1.3배를 기준으로 최대 1360으로 제한한다. 이는 **현재 동작의 기록이지 사용자가 최종 재확인한 개선안이 아니다.** 근거: [tape-input.js](../js/landing/tape-input.js), `js/landing/tape-input.js:4`, `:73`.

**검증 필요:** 전체 키보드 여정, 스크린리더 의미 전달, 색 대비, 터치·세로 화면의 손잡이 접근성. 좁은 화면은 원화를 cover로 자르므로 테이프 끝이 화면 밖에 놓일 수 있다. CSS의 700px 분기나 렌더 해상도 제한이 있다는 이유로 모바일 디자인을 완료했다고 말하지 않는다.

이전 랜딩은 네이티브 Canvas 2D 합성, 현재 랜딩은 DOM 원화 + Three.js, 앱은 Three.js다. 영상 프레임을 차례로 재생하는 구조도 아니고, Live2D 엔진을 사용한 구조도 아니다. 파일 형식 최적화로 원본 PNG의 실행 경로가 달라질 수 있으므로 **현행 manifest와 모듈의 URL을 먼저 확인**한다. 예전 `Vine_*`, `Comic_*`, SVG 상자 초안은 폴더에 존재한다는 이유만으로 활성 에셋이 되지 않는다.

같은 캔버스의 파츠를 잘라 각각 중앙 정렬하면 원근·합성·히트 영역이 무너진다. 크기나 원점을 바꿀 때는 manifest, sourceRect, 힌지, 접점과 드롭 영역을 함께 검토한다. 인코딩만 바꿀 때는 시각적 디자인과 그 좌표를 유지한다.

Fraunces는 [SIL OFL 1.1](../assets/landing/fonts/OFL.txt) 기록을 보존한다. Three.js는 `vendor/three/`의 라이선스 기록을 따른다. 생성 이미지의 프롬프트·분할 기록을 유지하되, 이 문서가 새 저작권·프로젝트 라이선스를 부여하는 것은 아니다.

## 앱으로 넘어갈 때의 디자인 경계

랜딩 마지막의 두 버튼은 모두 `app.html`로 간다. ‘내 파일로 시작하기’는 가져오기 화면, ‘체험해 보기’는 샘플로 3D 정리방에 바로 들어간다. 2026-10-08까지 이 화면 왼쪽 위에는 이전 프로젝트 이름 ‘정리대’(J 표시, PROTOTYPE 0-C)와 어두운 배경 `#10120f`, 라임 강조 `#d9ff57`가 있었다. 지금은 Cozium 워드마크와 위 [앱 화면 색](#앱-화면-색-2026-10-08-가져오기-화면정리방-공통)을 쓴다(사용자 결정: 어두운 계열). 실제 3D 정리방의 밝은 나무·종이 재질과 이 가져오기 UI는 구분한다.

**가져오기 화면: 노트북 바탕화면 (2026-10-18, 사용자 선택).** 랜딩이 노트북 화면으로 들어가 끝나는데 가져오기 화면이 그것과 이어지지 않던 게 가장 큰 문제였다. 세 안(노트북 바탕화면 그대로 / 게임 타이틀 메뉴 / 지금 구조에 색만) 중 사용자가 첫 번째를 골랐다. 이 화면이 곧 랜딩에서 들어간 그 바탕화면이다.

- 바탕: `desktop-v4/wallpaper.webp`(오른쪽 정렬 cover — 천창·선반·이불 그림이 늘 보이고 왼쪽 크림 벽은 아이콘 자리), 화면 테두리 `monitor-frame.svg`(9-slice 26 px), 작업표시줄은 `taskbar.webp`를 잘라 `assets/app/desk/`에 둔 막대(양끝 유지·가운데 늘림)·앱 타일 5개·트레이.
- 바탕화면 아이콘(왼쪽 위 세로): 샘플 바탕화면(폴더) → 샘플로 시작, 이용 안내.txt → help.html, Desktop Helper.zip → Helper 창.
- 작업표시줄 타일: 새싹 = 처음으로(랜딩), 폴더 = 가져오기 창, 사진 = 샘플, 문서 = 이용 안내, 모니터 = Desktop Helper. 트레이: Helper 연결 불(회색/초록) + 실제 시계(오전/오후 h:mm, 날짜).
- 가져오기 창 「Cozium으로 옮기기」: 제목 「내 바탕화면을 / 쓸어 담으세요.」(Fraunces 계열 + 겨자색 둘째 줄), 한 문장, 두 단계(진짜 바탕화면에서 Ctrl+A → 이 화면 아무 데나 끌어다 놓기), 20개 상자·한 번에 나오는 장 수·읽기 전용·개인정보·Chromium 전용 작은 글씨, 맨 아래 「파일 없이 샘플로 둘러보기 →」. 화면 **어디에** 놓아도 된다(끄는 동안 점선 테두리 + 「여기 놓으세요」).
- 놓고 나면: 놓은 것들이 진짜 바탕화면처럼 아이콘으로 깔린다(폴더 먼저, 위→아래 줄 채우고 다음 줄, 하나씩 점점 빠르게 나타남). 21번째부터의 폴더는 흐리게 + 「이번엔 빠짐」. 자리가 모자라면 마지막 칸이 「+N / 외 N개」. 가져오기 창은 오른쪽(그림 쪽)으로 비켜서고, 단계 안내 대신 「파일 N개 · 폴더 M개를 가져왔어요」와 진한 녹색 「방으로 가기 →」.
- 창은 제목줄을 잡고 끌 수 있고, 누르면 앞으로 온다. Helper 창은 그림 쪽 위에 열리고 ×로 닫는다. ?helper=로 들어오거나 연결되면 저절로 열린다.
- 방으로 떠날 때: 아이콘이 아래로 떨어지며(왼쪽부터 조금씩 시간차, 살짝 돌며) 창이 접히고 화면이 어두워진 뒤 방이 열린다(0.8초). 동작 줄이기면 바로. 시작이 실패해 이 화면에 남으면 되돌린다.

근거: [css/onboarding.css](../css/onboarding.css), [js/ui/import-desk.js](../js/ui/import-desk.js)(보이는 것만: 창·시계·아이콘·떠나는 연출), [app.html](../app.html)의 `#onboarding`. 파일 읽기·연결·시작은 그대로 [onboarding.js](../js/ui/onboarding.js)(요소 id 유지, `onRefresh`·`beforeStart`·`afterStart` 고리 추가). 이전 「밤의 방」(10-08, 방 그림을 어둡게 깔고 왼쪽 한 줄)의 그림(`parts/room-v3`, `parts/desktop-v2`)과 `js/ui/onboarding-room.js`는 더 안 쓴다 — GitHub 올리기(`tools/sync-to-c.ps1`)에서 뺐다.

재설계에서도 다음 의미는 보존한다.

- **랜딩 샘플:** 실제 파일과 관계없는 연출.
- **가상 파일 체험:** `MemoryProvider`, 실제 디스크 변경 없음.
- **웹 파일 가져오기:** `WebDropProvider`, 읽기 전용이며 정리 결과는 계획.
- **Helper 연결:** `NativeHelperProvider`, 허용된 바탕화면 범위에서 사용자가 놓는 순간 실제 이동·되돌리기·새 폴더가 반영됨.
- 실제 파일의 목적지는 사용자가 선택한다. 자동 추천·자동 이동을 디자인 연출로 숨겨 추가하지 않는다. 파일명을 보여 주는 이유와 실제 반영 상태를 흐리지 않는다.

## 성능 작업과 디자인 작업의 연결

Three.js 사용은 사용자가 허용했다. Unity·Unreal·PlayCanvas 같은 외부 엔진으로 바꾸는 것이 현재 요구가 아니다. 코드 줄 수나 파일 전체 용량만으로 화면이 느리다고 판정하지 않는다. 입력 지연, 그리는 픽셀 수, 필터·그림자, 이미지 디코딩과 불필요한 프레임을 실제 구현에서 확인한다.

성능 작업은 승인된 구도·에셋의 원점·조작 분기를 보존하면서 이미지 인코딩, 불러오는 시점, 유휴 렌더, 렌더 해상도를 조정한다. 화질 단계에서 외곽선·종이결·그림자 표현이 달라질 경우 그 한계를 기록한다. 낮은 해상도 모드를 모바일 재설계의 완료로 보고하지 않는다.

## 게임 픽셀 스타일 실험 · 2026-10-09

상태: 사용자가 1인칭을 유지한 시각 변경 실험을 승인하여 구현·자동 검증 완료. 최종 미술 방향의 사용자 확인은 대기 중이다.

게임의 원근 카메라·WASD·집기·파일 처리와 HTML UI를 유지하면서 선명한 파랑/테라코타 팔레트, 체크 바닥, nearest 텍스처, 각진 가구, 단순 침대, 하드 그림자와 밝은 환경광을 적용했다. RenderPixelatedPass는 화면 기준 6px, normal 0.5, depth 0.6으로 시작하며 추가 색 양자화·디더링은 없다. 기존 침대 GLB와 필터 경로는 보존했다. 랜딩·가져오기 화면은 이번 실험의 대상이 아니다.

세부 설정·복구 범위·비교 자료는 [픽셀 아트 스타일 실험](pixel-art-style.md)에 기록한다. 정사영/다른 구도 버전은 아직 구현하지 않았다.

## 정사영 비교 구도 · 2026-10-09

상태: 사용자 요청으로 카메라 설정에 정사영을 구현하고 자동 검증 완료. 기본 진입은 1인칭이며 설정 메뉴에서 즉시 왕복한다. 정사영에서는 방 내부를 볼 수 있도록 앞·오른쪽 벽과 걸레받이를 열고, 실제 OrthographicCamera로 원근 축소 없이 표시한다. 기존 사선·탑다운과 파일 조작을 유지한다. 세부 조절은 docs/pixel-art-style.md와 TUNING.camera.orthographic에 기록한다. 위 픽셀 실험 기록의 ‘정사영 미구현’ 상태를 이 기록으로 갱신한다. 최종 구도에 대한 사용자 시각 평가는 대기 중이다.

## Ordered dithering + PS1 vertex wobble · 2026-10-10
